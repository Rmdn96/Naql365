## Chosen authority design

Use a distinct guest capability, not a fabricated Supabase account and not a service-role proxy. Add private grant/verifier and abuse-budget records, an explicit guest Customer discriminator, and only the evidence actor fields required by that identity. Each guest Customer belongs to one journey; the grant binds its tenant and Request and resolves subsequent Quote/Order relations through existing foreign keys. A guest has no staff role or organization membership.

The server passes the guest capability only to a narrow database authority boundary using the public Supabase client role. Database verification checks a well-formed secret against its hash, scope, expiry and revocation on every operation. Anonymous raw table writes remain denied. Shared customer commands retain their state-machine, revision, replay and commercial invariants; only their customer authority/actor adapters change. Authenticated staff commands and `has_permission` must not acquire an anonymous bypass.

Guest secrets use at least 256 random bits. Raw secrets are returned only at issuance/replacement, never persisted server-side. The continuation URL carries the secret in a fragment so the hosting request path cannot log it. Exchange sets a secure HttpOnly SameSite cookie and redirects/navigates to a clean, noindex journey route. A same-origin bounded exchange and all later mutations are rate-limited. Staff can issue a replacement after authorized customer contact; old capability revocation and replacement are atomic and auditable without recording either secret. Never infer ownership from a reference, phone or email match. No automatic guest-to-account claiming.

Grant validity is configurable rather than hardcoded into business state. Expiry/revocation does not cancel a Request, invalidate an accepted Quote, change payment state or interrupt Driver execution. It only denies capability access. Reissue restores scoped customer access without recomputing commercial facts.

Guest live-map presentation is disabled for the initial MVP. Safe textual tracking is required and remains authoritative. This avoids introducing an anonymous Realtime authentication system merely for a presentation option. Existing registered live-map capabilities remain available under their established authorization.
