# Security and RLS implementation plan

No grants, policies, functions, Auth settings or database objects are changed now. The plan reuses inspected Supabase SSR identity, `customerClient` patterns, canonical permissions, exact-origin HTTP handling and `staffContext`; no new Auth or supplier identity system.

## Canonical context

Resolve configured storefront organization server-side; fail closed if missing/ambiguous. A registered buyer requires verified Auth, existing registered Customer in that org, active customer membership and `account.access`. Never bootstrap Guest Customers, convert STAFF/DRIVER or authorize by reference/email/user metadata. Do not union Customer relationships or staff grants across organizations. The current staff resolver requires exactly one active membership and that it is staff; preserve that behavior, not a weaker label-only check.

Store Market mutations validate an existing active organization-owned EG Market with EGP; SA Store is unavailable even if the public selector is SA. Locale/Market cookies are preference only. Reuse existing immutable foreign identities, never Transport requests/orders/payment permissions as Store authority. Role loss, suspension and revocation must be rechecked after lock waits and on idempotent replay.

## Explicit proposed permissions

The slash-separated Wave 6A groups below expand into distinct permission codes, not wildcard grants. Exact user/role assignments require owner approval. Existing SUPER_ADMIN, SALES, OPERATIONS/DISPATCHER, FINANCE and CUSTOMER_SERVICE role names do not automatically receive any new Store grant. No ACCOUNTANT or supplier role is introduced.

| Codes                                                                                                               | Required use / conjunction                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `store.catalog.read`, `store.catalog.manage`, `store.catalog.publish`                                               | Read drafts, edit retail/content, or publish/suspend respectively; publish requires read+manage+publish. No implicit source-cost read                                                        |
| `store.sourcing.manage`, `store.supplier_cost.read`                                                                 | Sourcing changes require both; restricted cost read alone never authorizes edits                                                                                                             |
| `store.orders.read`, `store.orders.manage`                                                                          | Operations read versus physical fulfillment/case commands; manage requires read. Does not confer Finance/cost                                                                                |
| `store.payments.read`, `store.payments.verify`                                                                      | Finance proof/collection review; verification requires both. COD operator report is not verified funds                                                                                       |
| `store.payment_accounts.manage`                                                                                     | Account version configuration requires this plus payment read, explicit eligibility approvals and maker/checker policy; not ordinary Finance by default                                      |
| `store.settlements.read`, `.prepare`, `.approve`, `.execute`, `.verify` (each with full `store.settlements` prefix) | Separate bounded settlement duties; detailed economics requires supplier-cost read. Execute does not imply independent verification; approved segregation must be enforced by actor identity |
| `store.refunds.read`, `.approve`, `.execute`, `.verify` (each with full `store.refunds` prefix)                     | Separate refund duties with approved original receipt/credit checks; execution report cannot self-certify money movement                                                                     |
| `store.support.read`                                                                                                | Narrow read-only safe customer journey/contact, no Finance evidence, supplier costs, catalog mutation or capability management                                                               |
| `store.audit.read`                                                                                                  | Redacted internal trace/reconciliation; paired underlying financial scope for sensitive financial facts                                                                                      |

Every staff operation also requires authenticated active staff in the selected org and `portal.access`. Read grants do not imply writes, and manage/execute codes are not wildcards. Customer own-order actions use ownership plus approved customer contract, not staff scopes. Future maker/checker actor rules, transaction thresholds and grants remain decisions, not defaults smuggled into a role seed.

## Relation-level RLS and function access

| Surface                                         | Intended policy / projection                                                                                                                                                                                                                                         |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public product/listing/category/media/retail    | Anonymous EXECUTE only on a bounded explicit retail projection gated by EG publication and approved policy. No direct access to broad base tables, offers, draft prices or private policy JSON                                                                       |
| Carts/items                                     | Active Customer ownership only; writes through guarded commands, no generic table INSERT/UPDATE/DELETE                                                                                                                                                               |
| Orders/items/events/adjustments                 | Customer reads via safe DTO, ownership and org/Market checks; staff reads through exact Store permission projection. Cost never embedded in otherwise readable row; event internal metadata excluded                                                                 |
| Agreements/offers/private supply terms          | Private schema or separately restricted relations; source-cost permission and same org/Market required. Catalog retail publication cannot serialize these fields                                                                                                     |
| Collections/allocations                         | Finance only raw receipts. Customer sees only their order's allocated payment summary; a receipt allocated to several orders must not reveal another customer's amount/contact/reference                                                                             |
| Proofs/files/accounts                           | Dedicated authorization by order/payment/proof purpose; customer instructions only the approved selected version when authorized, not account lists. Support/orders-read cannot download Finance proof. Public media path only after explicit derivative publication |
| Cases/refunds                                   | Customer own safe request/progress only; Operations sees physical return decision; Finance alone sees authorized receiving/refund evidence and execution. No customer update of state/amount approval                                                                |
| Supplier settlement/execution/financial entries | Private supplier/org/Market/currency context and exact settlement/refund scopes; no customer/Support access. Append-only posts/reversals via reviewed commands                                                                                                       |
| Command receipts / audit                        | Same reauthorized actor and scope for safe replay, or specific audit projection; no enumeration of mutation keys/outcomes across users                                                                                                                               |

RLS enabled before exposure on every new exposed relation. Revoke direct writes and default PUBLIC EXECUTE; grant minimal named functions. Prefer invoker reads; any SECURITY DEFINER command must have fixed empty search path, fully qualified objects, minimal owner, explicit Auth/membership/tenant/permission guards and no dynamic untrusted SQL. Test RLS separately from function checks because owners can bypass RLS. Private financial/source tables must not be reachable through PostgREST views with unintended owner privileges.

## File and transport boundaries

Separate Store purpose bindings; do not widen existing Transport `file_objects` policies or proof purposes as a convenience. Reserve → upload → immutable metadata validation → submit; no overwrite/upsert of submitted evidence. Validate type/size, normalize images, screen supported PDFs and use safe download disposition without claiming full malware detection. Signed links issued only after reauthorization, bounded expiry and no list exposure; no signed URL/path in analytics, general event JSON, logs or public SSR.

Retain canonical origin, Secure/SameSite/HttpOnly host-scoped cookies, PKCE/callbacks, role destinations and logout behavior. No wildcard callbacks, forwarded-host trust shortcut, new service-role application client or arbitrary Vercel alias acceptance. No Store Guest capability tables/functions in V1. Transport Guest tokens and references confer no Store access; Store resources cannot mutate Transport Orders or clear Trips.

## Required security evidence before implementation acceptance

For each projection/command test anon, CUSTOMER owner, another Customer, DRIVER, each restricted staff role with precisely scoped grants, and SUPER_ADMIN with/without explicit new permission. Exercise missing each conjunction, revoked/suspended/ambiguous membership, forged organization/Market/currency/supplier/order and stale resource revisions. Try direct REST/base relation, function EXECUTE, SSR/hydration/errors/exports/analytics and Storage access. Prove Customer/Support cost/notes/proof isolation and Finance account settings hidden without the separate grant.

Test permission revocation while a second connection waits on a lock; replay after role loss must deny, not return a cached sensitive success. Verify public catalog cache invalidation and checkout revalidation under suspension. Confirm no implicit role grants or existing policies/permissions changed after each future migration; independent Transport/Guest/Finance/Driver regressions remain mandatory.
