# Proposed Store command and API contracts

Names below are conceptual operation contracts, not implemented routes/RPCs. Future Next.js adapters use existing Supabase SSR sessions, canonical exact-origin HTTP protections and explicit input/output schemas. New SQL/API functions require separate approval.

## Common envelope and execution protocol

Mutation input: `commandVersion`, UUID `mutationId`, target resource identity, `expectedRevision` for mutable aggregates and a strictly validated command-specific payload. Create operations use an authenticated owner scope plus creation intent, not a fictional resource revision. Client IDs identify requested resources; organization, Customer, Market, currency, supplier, tax, authoritative price and effective permissions are derived/revalidated server-side. Authoritative money movements accept Finance-observed amount/reference as evidence inputs, validated against the obligation/eligible allocation rather than trusting customer totals.

Success: resource business reference, resulting revision, safe state/next permitted actions and replay flag. Customer result excludes source costs, account configuration, internal notes/proof paths. Failure categories: UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, VALIDATION, STALE_REVISION, TERMS_CHANGED, IDEMPOTENCY_CONFLICT, POLICY_UNCONFIGURED, MARKET_UNAVAILABLE, STATE_CONFLICT, RECONCILIATION_REQUIRED, RATE_LIMITED, TEMPORARY_SERVICE_FAILURE. Proposed HTTP mapping 401/403/404, 422, 409, 503, 429; ownership-hidden resources use 404 rather than confirm another customer's existence. Translate safe messages; no raw SQL/provider errors.

Validate auth/context before dedupe lookup and on replay. Scope dedupe to actor + organization + command version + mutation ID; canonical digest covers target and every meaningful business input, including expected revisions, but never passwords/tokens. Same authorized scope + digest returns the stored result; conflicting digest rejects. A lost HTTP response must not create another order, financial posting or execution intent. Concurrent same-key requests serialize on the receipt uniqueness; only successful committed outcomes are final. A rejected transaction leaves no partial facts; an external uncertain execution is a durable outcome, not a rolled-back permission to pay again.

Proposed page size default 20/max 50. Keyset cursor encodes timestamp/ID, stable sort and filter context; verify scope every request. Cursor is never authority. No fetching all pages to manufacture KPIs. Reads/private responses use no-store; public caching must include org/Market/locale/publication versions and invalidate suspension promptly before commercial revalidation.

## Lock order and race policy

Before locks, authenticate and discover candidate context; never return facts until reauthorized. All Store write functions use the same order: membership/auth-context rows → command receipt key → transaction-scoped financial scope lock `(org,market,currency,supplier)` where money/entitlement is affected → parent cart/order headers in sorted UUID order → fulfillment/payment/case headers in sorted identity order → source receipts/allocations/entries → policy/listing/version rows in deterministic order. Read-only key-share locks are sufficient for immutable referenced versions; checkout also locks mutable publication eligibility. Supplier/group scope is resolved from locked/revalidated database facts, never caller assertion.

Settlement/refund operations gather affected orders before acquiring financial locks, then lock/revalidate that exact set. Any changed membership/group/supplier set aborts and retries the transaction from the beginning; do not acquire a new lower-ranked lock midway. Catalog publication only takes catalog/version locks and must not then request order locks. COD/report/verification/return commands that change eligibility participate in the same supplier scope lock. No external network/upload/manual execution while holding a database transaction open.

Use expected revisions + explicit row locks + uniqueness and deferred aggregate constraints; isolation alone does not justify write-skew assumptions. Serialization/deadlock errors allow bounded database retry with the same intent, never repeat external execution. Recheck membership/revocation, state and approval after lock waits. Cancellation versus dispatch, payment verification versus cancellation, refund versus settlement and suspension versus checkout must each yield one coherent outcome or safe conflict. Transaction timeouts return unknown-outcome recovery using original mutation key, not a new key.

## UI integration boundary

Future Server Actions are thin typed adapters around these contracts. Client controls enable actions only from safe server projections; destination and command checks remain mandatory. Unknown Auth/backend failures must remain distinguishable from invalid credentials. Existing login/destination, exact canonical origin guard, callbacks, cookies, Transport guest grants and role shell behavior stay unchanged. No Store customer request calls Transport payment/Quote functions as a shortcut.
