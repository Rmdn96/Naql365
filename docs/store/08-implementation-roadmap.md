## Required future verification

1. Fresh database reconstruction and populated 47→approved Store upgrade; byte-identical migrations 1–47, existing Transport quotes/orders/payments/POD and grants commercially unchanged. No schema migration silently activates products, accounts, tax policy or suppliers.
2. Official generated DB types, SQL/RLS/direct REST/RPC/Storage negative tests and independent-connection races. Test checkout replay with lost response, conflicting idempotency payload, stale revision, price/suspension race, one cart→one order, wrong Market/supplier/tenant and ambiguous context.
3. Financial invariant tests using exact integer examples: COD supplier custody, Naql365 transfers, partial collection, fees/discount bearers, split receipts, returns before/after settlement, overpayment, duplicate references, competing refunds, settlement reservation versus return, reversal/dispute and unknown external execution. No duplicate payout/refund after timeout.
4. Full unit/integration/E2E, lint/strict types/format/build, runtime/development dependency review, tracked/history secret scans and exact-head required CI. Do not report source CI as evidence for a later test/evidence commit.
5. Hosted registered Customer, permission-restricted catalog/operator/Finance/Support, supplier-mediated fulfillment and payment/refund/settlement journeys through real commands. Guest only after approval. Check session/login/logout/Back, Customer/Staff/Driver boundaries and unaffected Transport regression.
6. Visual matrix across Arabic/English, RTL/LTR, SA/EG, Light/Dark/System and five widths. Include actual loading/empty/error/retry/validation/success and unconfigured states, keyboard/focus and axe smoke. Keep controlled visual simulations distinct from real business transitions; no fake financial success.
7. Scoped synthetic fixture ledger for every identity, order/line/group, proof/Storage object, collection, refund and settlement. Independently prove deletion/restoration of owned fixtures/configuration while preserving owner data. Dispose temporary credentials and verify denial/revocation where applicable; Preview remains protected.

## Operational rollout controls

Start disabled per Market, with no public prices/payment methods until approved complete configuration exists. Use explicit server-authoritative Store activation rather than a presentation flag. Promotion/release checks must verify artifact SHA, canonical origin, Staging project identity, protected access and immutable migration baseline. No arbitrary Preview aliases for Auth acceptance.

Agree order-value/quantity/page-size/rate limits, retention, supplier response/escalation responsibilities and reconciliation cadence before launch. Monitor safe command failures, unallocated collections, uncertain refunds/settlements and supplier exceptions; do not log secret/proof data. Fail closed for money authority but preserve evidence and recovery access to already placed orders if new sales are paused.

If a future release must be withdrawn, stop new Store placements and privileged executions while retaining read/reconciliation access and durable records. Do not roll back posted money or confirmed snapshots by deleting migrations. Transport must remain independently operational. Any irreversible data transformation or downgrade path requires its own reviewed plan.
