## Proposed new FK map — no existing-key alteration needed

Notation: `O=organization_id`, `M=market_id`, `C=currency`; these are column aliases for review, not SQL. New tables have UUID PK `id` and UNIQUE `(O,id)`. Market-owned new tables add `(O,M,id)`; currency-owned ones add `(O,M,C,id)` as needed for referenced relationships. All target keys below are ordinary nonpartial UNIQUE/PK constraints, never conditional indexes masquerading as FK targets.

| New relation / reference                       | Child tuple → target tuple                                                           | Finding                                                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Every new root                                 | `O → public.organizations(id)`                                                       | Existing PK supports it                                                                                                        |
| Policies, agreements, listings, offers, prices | `(O,M,C) → public.markets(organization_id,id,currency)`                              | Supported existing UNIQUE; C fixed EGP in this slice; EG country verified separately                                           |
| Products → category; category → parent         | `(O,category_id)` / `(O,parent_id) → store_categories(O,id)`                         | New UNIQUE; parent nullable, self/cycle blocked separately                                                                     |
| Agreement → supplier                           | `(O,supplier_id) → store_suppliers(O,id)`                                            | New same-tenant key                                                                                                            |
| Listing → product                              | `(O,product_id) → store_products(O,id)`                                              | New same-tenant key                                                                                                            |
| Offer → product                                | `(O,product_id) → store_products(O,id)`                                              | Same product identity, no assumed singleton supplier                                                                           |
| Offer → agreement                              | `(O,M,C,supplier_id,agreement_id) → store_supplier_agreements(O,M,C,supplier_id,id)` | Add this exact new target UNIQUE; agreement from another supplier cannot be substituted                                        |
| Price → listing                                | `(O,M,C,listing_id) → store_product_market_listings(O,M,C,id)`                       | Add exact new listing key; price belongs to selected listing                                                                   |
| Listing → selected price                       | `(O,M,C,id,selected_price_id) → store_market_prices(O,M,C,listing_id,id)`            | Add target UNIQUE; prevents selecting another product's listing price                                                          |
| Listing → selected offer                       | `(O,M,C,product_id,selected_offer_id) → store_supplier_offers(O,M,C,product_id,id)`  | Add target UNIQUE; prevents same-Market wrong-product offer                                                                    |
| Listing/price/agreement → policy refs          | `(O,M,C,policy_id) → store_policy_versions(O,M,C,id)`                                | FK establishes context; command/trigger additionally validates required policy kind, approved status and effective eligibility |
| Event → aggregate                              | Exactly one of eight typed catalog-parent FK fields using same-org/context target    | No arbitrary string/UUID polymorphic authority; events only catalog aggregates in this slice                                   |
| Event → receipt                                | `(O,command_receipt_id) → store_command_receipts(O,id)`                              | Receipt created before successful event; result JSON does not hold a reverse relational FK, avoiding cycle                     |

Nullable selected pointers are permitted for drafts. Mandatory published pointers require a row CHECK plus semantic command/trigger validation; MATCH SIMPLE on an intentionally null pointer must not accidentally bypass the all-required-fields publication check. Same-context identity columns are NOT NULL. FK enforcement does not imply permission or active/approved state.

## Circular dependencies and versioned content

Price references listing while listing selects price. Create listing with null selection, create offer/price relations, then add selection FKs; no temporary disabled constraints or nonexistent-table targets. Runtime saves an unselected draft first and atomically selects approved versions when publishing. Events reference resources and receipts, but neither resource nor receipt has an event FK; events are appended after resource mutation in the same transaction.

Do not let editing product/category draft text update public pages. Product stores mutable draft content/revision; each listing holds a validated immutable-at-publication retail content snapshot and `published_product_revision`. Explicit republish swaps the snapshot and selected price/offer/policy versions together. Events preserve the preceding publication fact. Product suspension is an independent immediate eligibility switch and does not rewrite snapshots. Category has separate draft and approved public name/path snapshot; public queries use approved fields only. Reparent/publish validates all ancestors and cycle freedom under the common Store catalog mutex. No product-version/history table is needed for this first slice; later placed order snapshots are separate immutable facts.

Agreements/offers/prices/policies have stable version-family identity plus version number, draft revision and approval facts. Draft terms may change under revision checks; approval freezes commercial content/effective interval. Revocation/suspension is separate monotonic eligibility metadata with an event. Changing approved money/terms requires a new version and explicit listing selection, never UPDATE of historical terms. A future date expiring does not automatically pick another offer/price.

## Unsupported assumptions resolved / deferred

- PostgreSQL row CHECK cannot validate another table's country, approval kind, tree ancestry or child sums. Use FKs plus guarded commands/triggers and serialized category/context mutations, not subqueries in CHECK.
- A time-dependent “active now” partial index is not an approval selector. Selected version IDs determine publication; read eligibility checks explicit effective interval at statement time. Version keys are unique, intervals validated, no automatic max(version) fallback.
- For minimal V1 the explicit selected pointer means multiple retained private historical/future versions may overlap without public ambiguity. If agreement policy later requires nonoverlap for a family, approve a separate serialized rule; do not promise an exclusion constraint requiring an unreviewed extension now.
- Public catalog never reads source costs, private policy evidence or raw event payload. Avoid `select *` and owner-privileged public views; explicit safe RPC only.
- Defer `store_files` and all media/Storage commands. No cart, order, fulfillment, settlement, refund, Customer or file FK is added now. Existing broad file/audit permissions are not reused.
- No live drift/DDL execution proof is claimed. The future exact SQL must compile on fresh 47 reconstruction and pass populated-upgrade checks before any apply.
