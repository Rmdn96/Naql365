# Versioned catalog command and publication contracts

Proposed database-only contracts for the first slice; not executed SQL or implemented APIs. Future app/UI wiring is separate. All operations use the new Store-only functions in [scope](02-exact-migration-48-design.md), not Transport commands.

## Common contract

Staff read: canonical Store scope resolved by database, session UID, exactly one active staff membership in that org, portal.access and required exact grants. Optional `p_org`/`p_market` can assert the intended context but must equal the derived scope; they never select another tenant. No command can create Store scope or choose SA/another currency.

Mutation envelope: operation/version, UUID mutation ID, target ID or null for create, expected draft/parent revision (required on update), bounded strictly typed payload. Actor/org/Market/currency/approval time derived from Auth/scope/server; no caller overrides. Proposed payload limit 32 KiB, depth/schema bounds, titles ≤200 chars per locale, SKU ≤80, slug ≤100, search ≤120, page default20/max50 and category depth ≤4. These are technical proposals for owner review, not product inventory/business quantity limits.

Retail amount is authored integer EGP minor units, strictly positive on approval, no default; supplier cost nonnegative only if deliberately supplied and documented, no default. Missing amount stays null in draft and cannot publish. Reject decimal/negative/overflow money; upper technical bound MAX_SAFE_INTEGER 9,007,199,254,740,991. No tax/discount/total/FX/commission calculator, customer checkout amount or financial settlement field is implemented here. Retail tax/display wording must refer to genuinely approved policy; unknown never becomes zero tax.

Success returns safe reference/ID/revision/state, applied version numbers and replay flag according to the caller's projection. Catalog workspace never returns supplier amounts. Error mapping proposed: unauthenticated/forbidden; ownership-hidden target not found; invalid payload; stale revision; conflicting mutation; policy unconfigured; Market unavailable; state/eligibility conflict; temporary service error. No raw PostgreSQL detail or private FK value. SQL optimistic conflicts should use an explicit bounded business conflict such as existing PT409 pattern, **not 40001**, which PostgREST may transparently retry; genuine serialization/deadlock may use bounded database retries with same intent.

## Version identities and immutable publication

| Entity         | Version identity / allowed changes                                                                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Product        | Stable SKU/product ID, integer draft revision. Save affects draft only; publish copies approved bilingual/specification/category presentation into listing snapshot and records source revision. Global product suspension separate from content |
| Category       | Stable ID/slug, draft revision and approved public content/path snapshot. Reparent/publish checks same org, ancestors and depth/cycles under common mutex; draft names never public                                                              |
| Agreement      | Family `(org,Market,currency,supplier,agreement_code)` + positive version. Approved terms/interval immutable; new version for changed terms, separate revoked/suspended metadata                                                                 |
| Supplier offer | Family `(org,Market,currency,supplier,product,offer_key)` + version. Each binds an exact agreement version and private unit cost; approval freezes them; future sourcing eligibility can be revoked without editing cost                         |
| Retail price   | Family listing + positive version, explicit amount/approved presentation policy. Approved amount/interval immutable; selection changes by publish, not automatic latest version                                                                  |
| Policy         | Family `(org,Market,currency,kind,policy_code)` + version; typed content, approval evidence/time, immutable approved payload; revocation ends future eligibility, not history                                                                    |

Draft version saves require expected revision. Approval checks required fields, actor/evidence and parent versions, then increments revision and freezes terms. Identities/org/Market/currency/parent bindings cannot be moved after creation. No lifecycle permits an approved row to return to editable draft; supersede/revoke and create a new version. Source/version IDs from a client must resolve to the exact database context/product/listing.

No hard delete API; abandoned drafts may stay private until a separately reviewed retention process. No guest access, price calculation, order placement, supplier availability check, file upload or fake business transition in these commands.

## Transaction and idempotency protocol

1. Authenticate and resolve canonical scope/operation before returning any dedupe/target fact. Acquire a dedicated transaction-scoped **Store catalog mutex for that org** (advisory key with a stable Store-only namespace); all catalog/category/product/supplier/policy/price/selection mutations participate. Hash collision can only serialize unrelated work, never grant access. Do not lock/update public.organizations or Transport resources for this purpose.
2. After waiting, re-resolve scope, active staff/membership and effective permission conjunction from fresh state. Ensure the context has not changed. Then create/lock command receipt keyed by `(actor subject,org,command family/version,mutation ID)`; operation/target/expected revisions/complete intent included in canonical digest.
3. Same authorized digest returns its original safe result; differing intent under same key conflicts. Do not return a sensitive prior sourcing outcome after losing cost permission. Same-key concurrent requests commit once; failed transaction writes no receipt/resource/event. A stale-version failure is not a successful mutation.
4. Lock relevant Store parents/children in documented order after the org mutex: supplier/agreement/policy → category/product → listing → offer/price; sort UUIDs within each tier. Single-org mutex prevents category A↔B write skew and publication-versus-suspension races. New future Store functions must not acquire this lock after acquiring money/order locks without a separately reviewed hierarchy.
5. Revalidate expected versions, current dependencies and eligibility. Write resource revision/publication selection, typed safe/private event and completed receipt as one transaction. No network calls, file uploads or legal/provider verification while locks held.
6. On unknown HTTP result, caller queries/replays original mutation ID, not a new intent. Public retail read uses one coherent statement snapshot and read-time eligibility; no independently fetched cost model or draft merge. Publication cannot produce partial old/new selection.

Activation/scope reconfiguration is excluded from this API; any future owner provisioning transaction must coordinate with the same context lock and explicit pause/revalidation plan. No command treats a role grant change as a successful cached authorization. Test post-wait revocation under independent connections; choose function volatility/isolation so fresh authorization/state is actually read rather than frozen in a stale transaction snapshot.

## Suspension/expiry semantics

Listing/product/category/supplier suspension, selected offer/agreement/policy revocation/expiry or inactive Market suppresses effective public visibility. Preserve publication snapshot and audit; do not delete a price or reinterpret any future historical order. Reads do not automatically swap to another price/supplier. Public response gives a safe unavailable/empty state; staff workspace can expose safe eligibility categories without supplier-cost detail.

Restoration may make a still-published listing eligible only if its exact selected approved dependencies are valid; product/listing explicit suspended state still requires authorized resume/republish. If the owner wants every source restoration to require a new publication, approve a stricter generation invalidation rule before implementation; do not present that alternative as already enforced. Existing Transport manual-pricing/configuration and service coverage remain untouched.
