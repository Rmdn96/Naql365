# Store security, RBAC and RLS design

Proposed future contracts only. No existing grants, RLS, Auth, cookies or callbacks change in Wave 6A.

## Identity and authority

Reuse Supabase Auth verification and active organization membership. Registered Store ownership additionally resolves the existing Customer relationship and `account.access`; a URL/customer ID does not establish ownership. Staff Store actions require an active **staff** membership, `portal.access`, selected organization and appropriate new Store permission. Extend the existing canonical resolver, not email, user-editable metadata, role labels or UI predicates. Never union grants across organizations. Ambiguous organization context fails closed, following `staff-context.ts`.

Proposed permission namespaces are additions requiring later approval; Transport `finance.verify`, `pricing.calculate`, `quotes.manage`, `operations.manage`, `guest.links.manage` and `support.read` do not automatically confer Store rights. `SUPER_ADMIN` is still organization-scoped and needs explicit canonical grants for new permissions, not a universal hardcoded bypass. No new ACCOUNTANT or supplier Auth role is proposed.

| Proposed Store authority                             | Allowed purpose                                                                                             | Exclusions                                                                                 |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Customer ownership                                   | Read own safe orders, edit own OPEN cart, place order, submit authorized proof, request cancellation/return | Costs, supplier agreement, Finance notes, settlement, other Customers                      |
| `store.catalog.read/manage/publish`                  | Staff catalog/content/retail-price drafting and controlled publication                                      | No inherent supplier-cost or Finance permission                                            |
| `store.sourcing.manage` + `store.supplier_cost.read` | Restricted suppliers, offers, agreements and cost snapshots                                                 | No payment/refund/settlement execution by implication                                      |
| `store.orders.read/manage`                           | Store order service, supplier communications, permitted fulfillment/cancellation commands                   | No confirmation of funds, private proof download or supply-cost exposure by default        |
| `store.payments.read/verify`                         | Finance payment queue, receiving evidence, verified collection/rejection                                    | Does not include accounts configuration, supplier cost or settlement execution             |
| `store.payment_accounts.manage`                      | Restricted future eligible collection destination configuration                                             | Separate from verification; production eligibility needs owner/legal approval              |
| `store.settlements.read/prepare/approve/execute`     | Separate supplier settlement duties, explicit cost-read dependency for detailed economics                   | No blanket customer-proof/receipt editing; maker/checker rules apply                       |
| `store.refunds.read/approve/execute`                 | Separate refund approval/execution and reconciliation                                                       | Customer/Support/ordinary Operations cannot execute; approver/executor separation proposed |

Suggested role grant review: SALES/catalog editors receive only explicitly approved catalog scopes; OPERATIONS/DISPATCHER Store operators only order/fulfillment scopes; FINANCE payment scopes and separately approved settlement/refund/account grants; CUSTOMER_SERVICE only the narrow support scope. Existing role membership alone grants none of these new Store permissions. Customer/Driver do not enter the staff Store shell; Staff/Driver are not automatically Customer shoppers. Exact grant combinations and self-approval prohibitions are owner decisions.

## Data and RLS boundaries

- Enable RLS on each new exposed relation; revoke default writes and private function execution. Restrict direct reads as well as command paths. Public catalog is an explicit allowlisted projection of active Market listings, localized content and retail prices, not `select *` over offers.
- Keep supplier cost/agreement/settlement data in private or separately restricted relations. Row-level security alone cannot hide cost columns on customer-readable order items. Customer RPC output schemas enumerate safe fields; nested JSON, errors, HTML/SSR, hydration, analytics and exports receive the same redactions.
- Commands revalidate Auth/Store guest authority, organization, Market, resource ownership, effective permission, revision and lifecycle inside a transaction. Definer functions use fixed empty search paths, qualified names, minimal owners and explicit execute grants. Do not let a function owner accidentally bypass the very checks it must perform.
- Composite FKs prevent cross-tenant/Market relations even in privileged import paths. Explicit active Market/account/offer validation remains mandatory. Market selection cookies and locale are preferences, not authorization or pricing authority.
- Same-origin writes retain existing exact canonical-origin checks, payload bounds, strict validation and safe error classes. No arbitrary Vercel origins, wildcard callbacks or service-role browser/runtime clients.
- Private proof/return/collection evidence uses reservation and immutable object binding. Owning an order grants only explicitly approved customer proof access, not generic Finance evidence. Support/general `files.read` must not expose Store payment proofs. Sign short-lived URLs only after reauthorization; do not return bucket paths in general order projections or allow overwrite/upsert after submission.
- Catalog media has a separate approval/publication boundary from private uploads. Validate size/type, normalize images, screen PDFs and use safe download disposition. Do not claim malware protection that is not implemented.

## Guest checkout contract (proposed, gated)

Existing Transport guests use `g1_` secrets, a Transport guest cookie/header, verifier-backed grants bound by FK to a specific Transport Request/Customer, and Transport-specific RPC/storage rules. Those are **incompatible as-is** with Store carts, Orders, returns and payments. Do not reuse a Transport token, grant table, cookie, RPC or Guest Customer bootstrap for Store.

Recommendation: registered checkout first. If Guest is approved, design a separate opaque Store guest session with high-entropy random secret, versioned Store-only namespace/cookie/header, verifier-only storage, finite approved expiry and revocation. An anonymous Store guest is not a fabricated Supabase Auth user, JWT or new CUSTOMER membership. Contact/address snapshots belong to the Store order; existing Transport guest identity assumptions remain untouched.

Private resource grants bind that Store session to a specific cart or order and enumerated customer-safe actions. Placement atomically adds the new order grant to the already-authenticated Store session and closes the cart, so a lost checkout response can safely replay without storing/revealing a new raw order token. A mutation receipt is scoped to the same authority and intent; knowing its identifier or order reference gives no access. Cart access must not imply arbitrary orders, and order access never implies staff, costs or Finance authority.

Require exact-origin exchange/mutations, Secure/HttpOnly/host-scoped/SameSite cookies, rate and replay limits, bounded verification, locks and post-lock expiry/revocation checks. No token in query strings, analytics, Referrer, server logs, screenshots or Storage paths; fragment exchange, if chosen, clears the fragment immediately and follows a reviewed CSP/referrer policy. Token/cookie/header names, lifetime, consent and recovery process remain design decisions, not configuration written now.

Transport capability presented to Store and Store capability presented to Transport must both fail. Logged-in Auth cookies cannot silently attach or upgrade a Store guest order; any claim/link process requires a separately reviewed proof-of-control transaction. Lost access must use an approved verified contact/recovery process, never reference-only lookup. Support read permission cannot issue replacement links; any later guest-access-management authority is separate, audited and explicitly approved. Store Guest implementation waits for approval of recovery, retention, CSRF, abuse/rate limits and cross-capability isolation tests.

## Negative test contract

Before acceptance, test each permission alone and missing conjunctions, suspended/revoked membership, ambiguous organizations, role loss while waiting for a lock, another Customer, another organization/Market, forged supplier/order/currency and direct REST/RPC/Storage requests. No link should appear solely because a destination later denies it, but hidden navigation never replaces command/RLS checks.

Test cost/notes leakage through public search/detail/cart/order/history, error JSON, SSR/hydration, exports and analytics; prove Support cannot mutate/read proofs and Finance without account permission cannot read configuration. Guest tests cover malformed/expired/revoked/replayed/session-swapped tokens, cart/order scope escalation, cross-Transport use and safe retries after lost responses. Financial concurrency tests must prove one posting/refund/settlement per authorized event and deny excess allocation. All fixtures are run-owned with independent cleanup; no owner identity or live financial account is required.
