The Phase 0 skeletons will be extended rather than replaced. New tables are justified only where the current schema has no entity for a stable source of truth: pricing configuration, pricing evaluations, evaluation components, and route-distance snapshots. Quote, quote-version, quote-item, and order columns remain on their existing tables.

## Architecture decisions

Pricing commands execute in PostgreSQL through narrowly granted functions. They derive the actor with `auth.uid()`, verify an active organization membership and an explicit permission, lock the relevant request/quote rows, and validate state transitions. The browser supplies validated planning choices and mutation identifiers, but cannot supply authoritative money, VAT, distance, version numbers, state, ownership, or order identifiers.

The evaluator uses integer halala throughout (`1 SAR = 100 halala`). Multiplication and percentage operations use integer numerator/denominator pairs with half-up rounding for non-negative values. Every persisted amount has a non-negative or explicitly bounded signed constraint and currency is initially `SAR`. The VAT rate is organization configuration expressed in basis points; each quote version stores the rate used, its VAT amount, and final total so later configuration changes do not rewrite history.

Pricing rules are organization-scoped, typed by the approved Phase 2 component codes, effective-dated, versioned, active/inactive, and expressed as an exact calculation mode with bounded parameters. A calculation stores its request identity, server-trusted planning inputs, distance snapshot, applied rule identifiers and versions, line components, and calculated subtotal. Recalculation creates a new evaluation; it never edits an earlier snapshot used by a quote version.

The distance boundary accepts normalized pickup and delivery references from the submitted request and returns a discriminated result: route distance in metres (plus optional duration), provider/method identifier, and calculation time, or an explicit unavailable reason. Provider credentials remain server-only. Straight-line distance cannot be labelled as driving distance. No approved live provider credential was found in repository configuration, process environment variable names, or Vercel environment-variable names during this analysis. Phase 2 hosted acceptance therefore requires either an approved live road-distance provider or an owner-approved deterministic operational alternative before Distance can pass.

A quote is the stable commercial aggregate for one submitted request. Each commercial revision is a new positive version. Draft versions may be changed only through a trusted Sales command. Sending locks the draft facts, assigns a concurrency-safe `Q-N365-YYYYMM-NNNNNN` reference if absent, stores immutable expiry (default 48 hours), and transactionally supersedes another active version. Database triggers reject updates and deletes of sent/history versions and their items except through narrowly controlled transition functions.

Customer view is limited to customer-safe `SENT`, `VIEWED`, `ACCEPTED`, `REJECTED`, `EXPIRED`, and `SUPERSEDED` versions owned through the related request. The first genuine view records one timestamp and one semantic event. Accept and reject lock the version and verify ownership, active membership, state, supersession, and `now() <= expires_at`. Acceptance assigns a concurrency-safe `O-N365-YYYYMM-NNNNNN` reference, updates the version, inserts exactly one order with commercial snapshots, and audits both changes in one transaction. Existing unique constraints provide the last database-level duplicate guard; retry returns the existing order.

## Security and testing implications

Direct authenticated writes to pricing, quotes, quote versions, quote items, orders, and audit logs remain revoked. Customers cannot read drafts or internal evaluation/rule/adjustment-reason records. Sales cannot cross organizations and customer metadata or email cannot grant permissions. Suspension invalidates both staff and customer paths through active membership checks.

Migration tests must reconstruct from zero and assert every constraint, function grant, policy, immutable trigger, reference format, and generated type. RLS and concurrency tests must cover cross-customer and cross-tenant denial, self-promotion denial, submitted-request immutability, concurrent calculation/version/send/accept flows, expiry boundaries, rejection, supersession, and one-order acceptance. Hosted acceptance must use a genuine Vercel Preview connected only to Supabase Staging and disposable fixtures. Production remains outside Phase 2.
