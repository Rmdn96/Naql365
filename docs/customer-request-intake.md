## Decisions

Use the existing operating-organization membership model. There is no pre-existing personal-organization lifecycle to reuse. A private operator-managed singleton enrollment setting selects the operating organization; public callers cannot choose it or any role. Onboarding derives auth.uid(), requires a confirmed identity, serializes retries per profile, creates only a customer membership/customer record and the fixed CUSTOMER grant, and never reactivates suspension. No email or editable metadata grants authority. Configure an isolated Staging organization and catalogues through a guarded operator setup, not customer data seeds or manual schema patches.

Core request data stays relational. A JSON RPC envelope is transport only; addresses, items and selections are validated and written to normalized tables. Draft writes lock the request, verify ownership and active membership, and compare a monotonic revision. The server returns a conflict on stale writes. Repeating the last mutation identifier returns its result without duplicating it. Submission validates the persisted complete draft and acquires a monthly counter with INSERT ON CONFLICT UPDATE, never MAX()+1. Retrying submission returns the already assigned reference. Submitted payloads are immutable to customers.

Phase 1 uploads accept JPEG/PNG/WebP images only, at most 3 MiB each and 8 files per draft. Reserve generated paths in a locked draft transaction, validate bytes and MIME server-side, upload privately using the user's session, then finalize association. Incomplete reservations are not submitted attachments. Removal is a retryable two-phase lifecycle: revoke read visibility, remove the Storage object, then remove the registry association. Cancellation marks pending cleanup; cleanup never removes schema/catalogues. No malware scanning is claimed.

Phase 2+ remains excluded: pricing, quotes, orders, dispatch, driver workflows, GPS, payments, messaging automation, AI, marketplace and billing.
