## 8. Guest ordering and public abuse controls

**READY architecture; OWNER INPUT REQUIRED for defaults; CONFIGURATION REQUIRED for activation.** `private.guest_policy` defaults disabled, lifetime 30 days (schema range 1–90) and organization-wide creations 30/hour (range 1–1000). No policy row is a closed gate. Owner must approve the values and customer support process before enabling; no assumption that 30 days fits every service duration.

Current server/database limits: creation per tenant/hour; mutation 60/minute per grant; request/proof upload reservations 60/hour per grant; exchange 300/minute per tenant (invalid attempts commit consumption); funnel telemetry 600/minute per tenant. JSON streaming body bound is 65,536 bytes; proof maximum 2 MiB (multipart bound 2.2 MB), request image maximum 3 MiB with database count/MIME enforcement. Budgets are not a complete DDoS/CAPTCHA solution: invalid rolled-back mutations do not necessarily consume a persistent budget, and a shared tenant quota can be exhausted by an attacker. Approve platform WAF/rate-limit monitoring and a peak-volume target; rehearse load on Staging rather than Production.

Guest secrets use a 256-bit capability, SHA-256 verifier at rest and fragment delivery; the app exchanges it for a Secure/HttpOnly/SameSite Strict/root `__Host-` cookie. Reference numbers/UUIDs are not credentials. All journey calls recheck scope/revocation/expiry. Staff with `guest.links.manage` use the existing Quote workspace link action and `/api/sales/guest-link` → `manage_guest_link(inspect|replace|revoke)`; replacement exposes a fresh value once and invalidates the old grant. Support must verify customer identity using an owner-approved procedure before reissue. Never send a secret in generic WhatsApp-prefilled text, analytics, logs or screenshots. Manual secure customer communication is required; no automated WhatsApp/SMS/email guest-link delivery is implemented.

## 12. Data protection and recovery

Supabase database backups cover database contents/Storage metadata, **not Storage object bytes**. Include Auth/project configuration recovery, keys/SMTP reconfiguration and user-session implications in the runbook; do not assume all dashboard settings are in migrations.

Application rollback selects a previously approved build compatible with the current schema; environment changes are not retroactively applied to an old build ; rehearse Hostinger artifact redeployment, with no instant rollback assumed. On first launch there is no prior Production application: the fallback is protected/closed intake or an approved maintenance response, not the old Phase 0 main build against a Phase 7 database.

Database rollback is not reverse SQL or deletion of tables. Stop writes, preserve evidence, identify the restore point, assess lost financial/operational records, restore only with incident authorization, reconcile Orders/Quotes/payments/receipts/Storage and verify invariants before resuming. Prefer reviewed additive forward fixes when feasible. Unknown migration ledger entries or type drift stop rollout.
